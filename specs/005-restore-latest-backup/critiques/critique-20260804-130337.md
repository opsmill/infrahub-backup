# Critique Report: Restore the Latest Backup Without Naming an Archive

**Feature**: `specs/005-restore-latest-backup` | **Date**: 2026-08-04 13:03 UTC
**Artifacts reviewed**: `spec.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/cli.md`, `quickstart.md`, constitution v1.1.0
**Reviewed against code**: `src/cmd/infrahub-backup/main.go`, `src/internal/app/{backup.go,backup_s3.go,retention.go,s3.go,snapshots.go,plakar_restore.go}`

## Executive Summary

The spec is tight: it descends from a maintainer-confirmed idea brief, every FR is
testable, scope is aggressively bounded, and the design reuses the retention
primitives instead of inventing a second ranking. The plan is constitution-clean on
four of five principles as written — but the engineering review found **one real
data-integrity flaw in the plan's S3 delegation mechanics** (research D3): reusing
the positional-`s3://`-URI restore path can silently truncate and then delete an
operator's pre-existing local copy of the same archive. That is exactly the class
of failure constitution Principle II exists to prevent ("recoverability is the
product"), so it is a Must-Address — resolvable with a contained design change, no
spec impact.

**Verdict: ⚠️ PROCEED WITH UPDATES** — fix E1 in `research.md`/`plan.md`/
`contracts/cli.md`, then proceed to `/speckit-tasks`.

## Engineering Lens Findings

**4a. Architecture Soundness** — Selection composing in front of an untouched
`RestoreBackup` is the right shape; shared-core placement satisfies constitution I;
reuse of `storageLocation`/`sortBackupRefsNewestFirst` makes FR-005 structural.
No findings.

**4b. Failure Mode Analysis** — **E1 (🎯 Must-Address)**. Research D3 delegates the
S3 leg as `RestoreBackup("s3://<bucket>/<key>")`, reusing `downloadBackupFromS3`.
Verified against the code:

- `downloadBackupFromS3` downloads to `filepath.Join(cfg.BackupDir, filepath.Base(key))`
  (`src/internal/app/backup_s3.go`), and `S3Client.Download` opens that path with
  `os.Create` — which **truncates an existing file** (`src/internal/app/s3.go`).
- `RestoreBackup` then runs `defer os.Remove(actualBackupFile)` on the downloaded
  path (`src/internal/app/backup.go:314`).

`create --s3-upload` with keep-local populates *both* pools with the same
newest archive name. On such a host, `restore --latest --s3` would resolve that
name, truncate the operator's local copy with the downloaded bytes, restore, and
then **delete the local copy** — a silent loss of a backup artifact, violating
Principle II. The positional `s3://` form has the same latent behavior today, but
`--latest --s3` turns a rare manual collision into the *expected* state of its
primary flow.

*Suggestion*: in the `--latest --s3` leg, do not round-trip through the URI path.
Download with the **same configured client that performed the listing** to a
collision-proof temporary path (e.g. `os.CreateTemp(cfg.BackupDir, "restore-latest-*.download")`
— a name that deliberately does not match `backupNamePattern`, so a failed cleanup
can never pollute the pool for retention or subsequent `--latest` runs), restore
from that path, and remove it afterwards. Existing positional-URI behavior stays
untouched (out of scope; worth a separate follow-up issue).

**4c. Security & Privacy** — No new trust boundaries: same credential chain
(env/file/IAM — verified `NewS3Client` ignores config for creds, so listing and
download authenticate identically), same encryption handling; the fail-fast gate
must use the same decrypt-key value that is passed to `RestoreBackup` (the flag
parameter — the `viper.BindPFlag("decrypt-key", …)` binding is not read back
anywhere, verified by grep), which the plan already does. No findings.

**4d. Performance & Scalability** — One listing per invocation, pools bounded by
retention; `s3ListTimeout` (5 min) already bounds the S3 listing. No findings.

**4e. Testing Strategy** — Solid unit/e2e split mirroring spec 004. Add one table
to the plan's test list: the temp-download-name property from E1's fix — the
downloaded temp path must never match `backupNamePattern` (**E3**, 💡).

**4f. Operational Readiness** — FR-009's single pre-restore log line is the audit
contract; exit-code table is complete; no migrations; rollback = don't pass the
flag. No findings.

**4g. Dependencies & Integration** — No new dependencies (no vendorHash churn);
plakar path untouched; Docker-Compose service contract untouched. No findings.

## Cross-Lens Insights

- **X1** (= E1 viewed from product): a backup tool that can destroy a backup copy
  while restoring erodes exactly the trust the P1 persona (unattended nightly sync)
  depends on — nobody is watching the job to notice the local copy vanished. The
  engineering fix is small and the product risk it removes is large; highest
  priority item in this report.
