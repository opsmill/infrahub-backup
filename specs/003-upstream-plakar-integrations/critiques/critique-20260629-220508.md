# Critique Report: Rework Plakar backend onto upstream database integrations

**Date**: 2026-06-29
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ PROCEED WITH UPDATES

---

## Executive Summary

The spec and plan are strong: a clear problem (stop maintaining bespoke dump/restore mechanics), well-sliced independently-testable stories (postgres MVP → neo4j enterprise → neo4j community → upstream reusability), measurable success criteria, and an honest, decision-gated technical approach (the consumption-model spike, the inside-container runtime, the clean break). The design's separation — Infrahub orchestration in the tool, reusable mechanics in the integrations — is sound and testable.

Two findings rise to **Must-Address** before tasks: (E1) the in-process runner reuses *our* binary, which also embeds host-orchestration (docker/kubectl) — the in-container connector-run path must be a dependency-light entrypoint, or the runner image inherits orchestration deps it should not have; and (E7) consuming `integration-postgresql` at a **beta** release to back up production data is a data-safety risk that needs an explicit pin + restore-round-trip validation gate. Both are resolvable with plan refinements (applied below), so the verdict is PROCEED WITH UPDATES, not RETHINK. The remaining items are recommendations recorded for implementation.

## Engineering Lens Findings 🔬

### Architecture Soundness
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | In-process consumption makes the runner = our binary, but that binary also embeds orchestration (docker/kubectl detection, env backends). Run *inside* the DB container it must not need those. | **Define a dependency-light connector-run entrypoint** (e.g. a hidden `__run-connector` subcommand) that only opens the repo + runs the connector op; the runner image must not require docker/kubectl. (Applied to plan.) |
| E1b | 💡 | Same binary in two modes (host orchestrator vs in-container runner) risks config/flag bleed. | Keep the runner entrypoint's flag/env surface minimal and explicit; document the mode boundary. |

### Failure Mode Analysis
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E2 | 💡 | Ephemeral runners (containers/Jobs) can leak if the tool crashes mid-run; and the neo4j writer must be *fully* stopped (not paused) before an offline dump to avoid store inconsistency. | Label ephemeral runners and reap orphans on start/abort; add a writer-stopped verification gate before community offline dump. (Applied to plan/runner contract.) |

### Security & Privacy
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E3 | 💡 | DB and S3 credentials injected as `-e`/Job env are visible via `docker inspect` / pod spec. | Prefer passing secrets via stdin/file or a K8s Secret reference rather than inline `-e` where feasible; at minimum avoid logging them. |

### Performance & Scalability
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E4 | ✅ | Single-deployment scale; per-component runner-start overhead is negligible vs dump time. | No change. |

### Testing Strategy
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E5 | 💡 | K8s E2E parity (SC-008) needs an ephemeral cluster (kind/k3d) in CI; testcontainers needs Docker-in-CI. | Plan the CI test infrastructure explicitly (kind for K8s E2E, Docker for testcontainers); mark the heaviest E2E as a gated/nightly job if needed. |

### Operational Readiness
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E6 | 💡 | Runner output must be captured and surfaced (today the tool streams exec output); clean break means no backup-format rollback. | Stream/capture runner logs to the tool's output; document that rollback = restore with the prior tool version (P4). |

### Dependencies & Integration
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E7 | 🎯 | Backing up production data via `integration-postgresql` at a **beta** release (v1.1.0-beta.7) is a data-safety risk if the integration changes format or has bugs. | **Pin the exact version, gate adoption on a backup→restore round-trip validation test, and track the stable release for upgrade.** (Applied to plan risks.) The new neo4j integration is ours, so we control its quality. |
| E7b | 💡 | In-process path needs a `go.mod replace`/version alignment across kloset; this is a maintenance coupling. | Prefer aligning everything to the stable `v1.1.0` kloset line; document the replace if the spike requires one. |
