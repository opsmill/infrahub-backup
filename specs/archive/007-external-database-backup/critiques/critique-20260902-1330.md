# Critique: External Database Backup and Restore

**Feature**: 007-external-database-backup | **Date**: 2026-09-02
**Artifacts reviewed**: spec.md, plan.md, research.md, data-model.md, contracts/, quickstart.md
**Constitution**: v1.1.0
**Note**: the `critique` extension is registered in `.specify/extensions.yml` but ships no
`critique-template.md`; this report follows the structure the command prescribes.

## Executive Summary

The design is sound and the problem statement is now accurate — Phase 0 confirmed the transient-pod
approach is the database vendor's own documented topology, and it already overturned two of the
author's assumptions, which is evidence the research was doing real work rather than confirming a
preference.

The weaknesses are not in the architecture. They are in **the seams between this feature and code
that already exists**. Three of the seven must-address findings are cases where a new requirement
cannot actually be satisfied by the module that owns the behaviour (retention, metadata versioning,
command timeouts), and were verified against the source rather than inferred. One is a security
surface the spec creates and does not mention. One is a genuine single-point-of-failure in the half
of the round trip the feature owner explicitly insisted on.

None require redesign. All are additive requirements or bounded decisions.

**Verdict: ⚠️ PROCEED WITH UPDATES**

## Product Lens Findings

### 3a. Problem Validation

**P1 💡** — The spec's evidence for demand is the phrase "several customers". No count, no accounts,
no ticket references. That is thin for 23 functional requirements, a new destructive operation, and
a new cluster permission requirement. More pointedly: the single most load-bearing assumption in the
feature — that customers will grant pod-creation rights (FR-019) — was resolved by assumption, and
the customers who could answer it definitively are identifiable and already asking for the feature.

*Suggestion*: before implementation starts, confirm the permission question with one named customer.
It is a single question, and a "no" would promote User Story 3 to P1 and change the task breakdown
substantially. This is the cheapest de-risking available.

### 3b. User Value Assessment

**P2 💡** — The tool already ships `environment detect` and `environment list`. An operator whose
backup just failed will run `environment detect` first, and the spec says nothing about what it
reports for a deployment with an external database. Today it would presumably report the environment
as found while the thing the operator cares about — that the database is not in it — goes unmentioned.
User Story 2 exists to make this population diagnosable, and it addresses the backup path only.

*Suggestion*: add an acceptance scenario to User Story 2 covering `environment detect` reporting
external database locations. Cheap, and it meets operators where they already look.

The MVP shape is otherwise right: US1 is one indivisible slice because a round trip that does not
close has no value, and US2/US3 are correctly deferred.

### 3c. Alternative Approaches

**P3 💡** — Research R1 rejected `--to-path` writing directly to cloud storage in order to preserve
the Plakar pipeline. Correct for feature parity, but it means a customer who wants only "a backup in
our bucket" is being routed through substantially more machinery than they need. The rejection is
recorded in research and invisible to users.

*Suggestion*: document it as a supported manual escape hatch. Costs nothing, and it gives support a
one-line answer for customers who cannot meet the seed prerequisites.

### 3d. Edge Cases & UX

**P4 💡** — FR-012 keeps incomplete artifacts out of restore-point selection, and scheduled restore
selects the latest backup. Together these mean a scheduled restore can silently use an *older*
recovery point than the operator expects, with no signal that it skipped one.

*Suggestion*: require that skipping an incomplete artifact during automatic selection is reported,
not merely done.

Accessibility and localisation are not applicable to this surface. Error, empty and failure states
are unusually well covered by the CLI contract's wording table.

### 3e. Success Measurement

**P5 💡** — SC-001–008 are measurable but all are pre-release acceptance gates. There is no
post-launch signal and no rollback trigger. For a backup feature the obvious signal is whether
customers' scheduled backups are completing, and the obvious rollback trigger is any artifact that
fails at restore.

*Suggestion*: add one post-launch criterion and name a rollback trigger. Also note SC-003 is phrased
as a property of the test suite ("no test case produces…") rather than a user outcome.

## Engineering Lens Findings

### 4a. Architecture Soundness

**E6 🎯** — Pod resolution falls back to **substring matching on pod names**
(`environment_kubernetes.go:305-313`, and the same fallback in `getAllPodsWith`). The transient pod
must contain the canonical service name for that fallback to find it — but the same property makes it
visible to every other caller of that resolver. `GetAllPods` and `ServiceReplicas` feed replica
counting and the `infrahub-collect` bundle, so while the pod exists it would be reported as a
replica of the `database` service. A troubleshooting bundle collected during a backup would describe
a database replica that is really a backup client.

*Suggestion*: make the transient pod's name and labels explicitly excluded from the shared resolvers,
and add a unit test asserting `GetAllPods` does not return it. Registering it in the cache under a
canonical name must not mean it is discoverable *as* that service.

### 4b. Failure Mode Analysis

**E1 🎯** — **The remote backup command has no timeout.** The 30-minute guard
(`defaultStreamIdleTimeout`, `backup_neo4j.go:108`) protects only the *data stream*. For the
Enterprise path the backup command is deliberately run as a separate step before any streaming
("Run backup command separately so its stdout logs don't contaminate the data stream",
`backup_neo4j.go:40`), and that step goes through `iops.Exec`, which uses the **unbounded**
executor — the code comments in `environment_kubernetes.go` say so explicitly, contrasting it with
the timeout-bounded runner the collect primitives use.

In-cluster this was tolerable: the database was a pod one had other ways to observe. An external
database that accepts the connection and then stalls — a checkpoint on a very large store, a network
partition mid-transfer, a firewall dropping an idle connection — hangs the tool indefinitely, with
Infrahub possibly still scaled down if this happens on the restore path. Research R1 flagged
checkpointing as a known cause of backup stalls.

*Suggestion*: bound the remote capture with a timeout, defaulting generously and overridable, and
reuse the existing bounded runner rather than adding a mechanism. This is the finding most likely to
produce a support incident.

**E4 🎯** — The restore sequence replaces the database Infrahub connects to, while Infrahub is
scaled down and then scaled back up. Two things are unspecified: whether a scale-down completes
before the replace begins (task workers retry, and termination is not instantaneous), and whether
scaling back up is sufficient for Infrahub to bind to a *recreated* database rather than a restarted
one. If it is not, the restore reports success and leaves a non-functional instance — a Principle II
failure mode arriving through the back door.

*Suggestion*: specify the ordering as a requirement (quiesce confirmed before the destructive step),
and add an acceptance scenario asserting Infrahub serves data after scale-up without manual
intervention. Quickstart Scenario 3 asserts the data is served but not that no manual step was needed.

**E2 🎯** — **FR-012 cannot be satisfied by retention as it exists.** Retention decides entirely
from artifact *names*: `parseBackupName`, `backupTimestamp`, `sortBackupRefsNewestFirst`, and
`retentionKeeps(ref, rank, policy, now)` where Count "keeps the Count most recent backups at a
storage location" by rank (`retention.go:238-310`). It never opens metadata for any decision.

So an artifact marked `capture_complete: false` still occupies a rank slot, and under a Count policy
it **evicts a good backup** while itself being unusable as a restore point. The requirement as
written silently assumes retention is metadata-aware. It is not, and making it so is a change to the
largest and most heavily tested module in the codebase (919 lines, 2123 lines of tests).

*Suggestion*: decide explicitly between (a) teaching retention to read metadata, (b) encoding
incompleteness in the artifact name so the existing name-based logic can act on it, or (c) never
retaining an incomplete artifact at all — write it, report it, and delete it. Option (c) is the
smallest change and the safest default; (b) is a naming-contract change. This decision belongs in the
spec before tasks are generated, because it determines whether `retention.go` is touched at all.

### 4c. Security & Privacy Review

**E5 🎯** — Two problems in one place, both created by this spec.

First, the transient pod's image is operator-declared (FR-004) and, per the binding convention in
the CLI contract, settable by environment variable. Combined with the pod-creation rights the feature
requires, that is a mechanism for running an **arbitrary container image in the customer's namespace**
by influencing the tool's environment. The threat model is not stated anywhere.

Second, the pod spec has no `securityContext`. Hardened clusters enforcing restricted Pod Security
Standards will reject a pod that does not declare `runAsNonRoot`, drop capabilities, and disallow
privilege escalation — and hardened, compliance-driven estates are precisely the population that
runs its databases outside the application cluster. The feature could be unusable for its own target
audience. Note also that the vendor documents the backup command as needing to run as the database's
own user, so the security context and that requirement must be reconciled rather than assumed
compatible.

*Suggestion*: add a requirement that images resolve from an allowed registry or a pinned default with
the override requiring an explicit flag rather than ambient environment; and specify the pod's
security context, validating against a restricted-PSA namespace in the end-to-end suite.

Also worth stating (💡): credentials for an externally-managed database now pass through the tool's
own process and into the cluster API, where previously they never left the database pod. FR-014 and
FR-023 cover storage and lifetime but the widened trust boundary is not acknowledged.

TLS deserves a mention too (💡): Infrahub's config carries `INFRAHUB_DB_TLS_INSECURE`, and if the
tool inherits it, credentials cross the network without certificate verification.

### 4d. Performance & Scalability

No must-address items. FR-022 now covers scratch sizing with a queried size and headroom, which was
the main exposure. Two notes: the headroom factor is unquantified, and the capture adds a full
database-sized transfer *inside* the cluster that did not exist before, which is worth stating for
capacity planning in large deployments.

### 4e. Testing Strategy

**E7 💡** — The plan describes the end-to-end work as "a fixture change — where the database runs and
what the application's environment says". That understates it: the suite must stand up a database
**outside** the cluster under test, reachable from inside it, with an Enterprise licence, plus an
object store the database itself can reach. That is new CI topology, not a fixture parameter.
Principle IV makes this non-optional, so under-estimating it risks the requirement being quietly
dropped.

*Suggestion*: treat the CI topology as its own task with its own estimate.

The two-concurrent-runs scenario also has no obvious home in the current suite.

### 4f. Operational Readiness

**E3 🎯** — `BackupMetadata` carries `MetadataVersion` (currently `2025111200`), and Principle II
requires restore to "refuse incompatible versions unless the user explicitly overrides". The spec's
compatibility story (FR-016, artifact contract) covers only new-tool-reads-old-artifact. The reverse
is unaddressed and forks badly:

- If adding fields bumps `metadataVersion`, an older binary **refuses** the new artifacts — so rolling
  the tool back after an upgrade strands every backup taken in between.
- If it does not bump, an older binary ignores unknown JSON fields silently — including
  `capture_complete` — and will therefore **restore an artifact this feature marked incomplete**.

*Suggestion*: choose deliberately and record it. The defensible choice is not to bump, and to encode
incompleteness where an old tool cannot miss it — which converges with E2's option (b) or (c).
Whichever is chosen, add a test that pins the old-reads-new behaviour, because right now it is
accidental either way.

Observability is otherwise adequate under Principle V, though nothing emits a signal an operator
could alert on for "external mode engaged" (💡).

### 4g. Dependencies & Integration Risks

**E8 💡** — ADR-0007 establishes offline-by-default, and its rationale states the general position:
"offline-by-default is the correct posture for an ops tool that runs in restricted networks." Its
*decision* is scoped to `infrahub-collect`, so this feature does not violate it — but it does cross
that posture for `infrahub-backup`, and unlike the benchmark's opt-in pull, this one cannot degrade
to "skipped" because it is load-bearing. ADR-0007 also supplies the pattern worth copying: an
overridable image variable so air-gapped-with-private-registry keeps working, which FR-004 already
provides.

*Suggestion*: record an ADR for the posture change. It is the kind of decision a future maintainer
will otherwise read as an oversight.

The dependency on the AWS command-line tool being present on customer database servers has no
version constraint stated (💡).

## Cross-Lens Insights

**X1 🎯 — Restore is a single mechanism whose prerequisites are least likely to hold for the target
population, and both fallbacks were explicitly rejected.**

The product lens and engineering lens converge hard here. Remote restore requires the cloud seed
provider, which requires the AWS command-line tool installed and credentials configured **on every
Neo4j server** (research R2). The customers who put their database outside the application cluster
are disproportionately those with locked-down, centrally-administered database estates — the ones
least able to add tooling and credentials to a database host.

If that prerequisite cannot be met, the round trip does not close. And the spec has already rejected
both alternatives: operator-staged artifacts (breaks the no-manual-steps promise) and
PostgreSQL-only restore (different recovery points). Research R2 noted `dbms.recreateDatabase()` as
"a genuine second option… worth revisiting if the seed prerequisites prove onerous" — with no
criterion for when that revisit is triggered.

Every other risk in this feature degrades to a clear error. This one degrades to "the feature does
not work for you", discovered after the backup half has been built and shipped.

*Suggestion*: validate the seed prerequisite against a real target customer's database estate before
implementing the restore half, and record a decision criterion for falling back to the recreate
procedure. This is the same de-risking action as P1 and can be the same conversation.

## Verdict

⚠️ **PROCEED WITH UPDATES**

No finding requires redesign. E1, E4, E5 and E6 are additive requirements. E2 and E3 are bounded
decisions that converge on a single choice. X1 and P1 are one customer conversation that should
happen in parallel with implementing the backup half — it does not block starting, but it should
block *finishing* the restore half.
