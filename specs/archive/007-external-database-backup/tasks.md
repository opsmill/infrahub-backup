## Scope notes

- **User Story 3 (operator-host execution) is deferred** and generates no tasks. It stays specified
  as the defined consequence if the transient-workload permission assumption fails.
- **Two tasks cannot be completed on a developer machine** and are marked `[INFRA]`: T072 (CI
  topology) and T073 (customer prerequisite validation). They gate *finishing* the feature, not
  starting it. See the critique's X1 and E7.
- The design's success indicator is that the ~93 call sites naming `database` and `task-manager-db`
  are **not** edited. Any task that would edit them is a signal the stand-in approach has leaked.
- **Phase 3 was implemented and then reverted** (`4de8d3c`), then rebuilt on the corrected
  foundation. Its code was written against three decisions since shown wrong — merged stdout/stderr,
  `podCache` routing, and edition-by-container-exec — so Phase 2S landed first. The rebuild names the
  exec target with `ExecOptions.Pod`, parses stdout alone, and reads an external server's edition over
  Bolt at the gate rather than by exec'ing a container that is not there.
- **A chunk's passing tests do not mean the code runs.** Five requirements in this feature had full
  unit coverage and zero non-test callers, and the transient pod could never have been admitted by a
  kubelet. Before reporting any task done: grep for a non-test caller of every symbol it adds, and
  verify any premise about an external artefact (a container image, a vendor CLI, an API) with a
  named command rather than asserting it.

## Phase 2T: Post-remediation review findings

A `max` review over the 25 remediation commits (10 angles, 71 candidates, 15 verified plus 8 cut by
the cap). **Every one is the same class: a new single-source-of-truth was introduced and an older
parallel answer was left standing.** Several are regressions the remediation itself introduced.

Findings 1–7 were dispatched to a fix chunk; the rest are recorded here. **Locate by symbol — line
numbers in this file have drifted three times.** Acceptance test for the class:
`grep -rn nameMatchesService src/ | grep -v _test` must return nothing outside `kubernetes_ownership.go`.

### Silently wrong or destructive

- [X] T097 `getPodStatusesWith` aborts on any selector error where the deleted code fell through to a namespace-wide listing — and `stopAppContainers` swallows that error and continues. On a Helm deployment (where the fallback is the *only* thing that ever matches `infrahub-server`) one throttled kubectl call yields a cold `neo4j-admin dump` with writers still running, reported as success. **T075 and T082 are each correct alone; together they corrupt a backup**. Fixed on both sides: the fallback listing now answers a selector failure — it enumerates every pod with the ownership evidence its labels carry, so it is a superset of what any selector could match, and only the listing *also* failing is undetermined (both failures reported); and `stopAppContainers` now fails the run on an undetermined status instead of warning and continuing, since every caller is about to require the services down. It still stops nothing on a guess
- [X] T098 `declaredServiceIn` returns the first *present* key's value rather than the first that names a service, so a chart with `app: <release>` on every pod masks `infrahub/service: <service>` — no pod contributes ownership evidence, the prefix set is empty, and an in-cluster database is declared external. This is the mechanism T075/T078/T082 all rest on. `declaredServiceIn` and `parseLabelledPods` — the workload half and the pod half of the same read — both take the first label value that names a service in `infrahubServiceLabelValues`, through the one new gate `declaredServiceValue`, rather than the first key that is set. A chart-labelled namespace (`app: <release>` plus `infrahub/service: server`) recovers its release prefix again. This is what makes T097's fallback a superset
- [X] T099 Transient pod and secret names are `<prefix>-<role>-<runID>` with **no service**, while the run ID is minted once per run — so both databases external means two workloads under one name, an `AlreadyExists` abort blaming a concurrent operator, or a Postgres pod holding Neo4j's credentials. Caused by this effort's own instruction to mint the run ID per run without adding the service to the name. `podName` is now `<prefix>-<database>-<role>-<runID>` and `secretName` is derived from it, so one run's two databases are two pods and two secrets. **The database segment is `neo4j`/`postgres`, not the deployment service name**: T074's hazard is deliberately not created — neither `database` nor `task-manager-db` appears in any transient object name, and a test asserts that plus the 63-character DNS-label limit
- [X] T100 `resolveExternalTLS` sets Neo4j `Encrypt = tls.Enabled`, so a deployment not exporting `INFRAHUB_DB_TLS_ENABLED` sends this tool's own database password unencrypted out of the cluster, with no flag to force TLS on. The same file argues at length that a discovered `tls_insecure` must be read and never obeyed. Encryption is the default for both databases and `--external-db-insecure-tls` is the only thing that turns it off; with the flag the channel is the weakest the deployment describes (unverified where it declares TLS, unencrypted where it does not). No new flag, so the decision stays two-valued and `--external-db-tls-policy` stays removed; `contracts/cli-surface.md` records the widened opt-out
- [X] T101 On the Plakar backend an incomplete capture is committed and reported successful: components commit one at a time, the completeness refresh sits on the metadata component reached *last* and so is unreachable with a false value, and `buildSnapshotTags` stamps `StatusComplete` unconditionally. The tarball path deletes the artefact and fails. The unreachable completeness refresh is replaced by FR-012's gate, raised before the metadata component is created — the last moment nothing is listable — and a deferred `discardPlakarComponents` deletes the component snapshots the run had already committed on every exit path, which is `discardIncompleteCapture` for this backend. `buildSnapshotTags` was already fixed by `2a5f326`
- [X] T102 `CaptureComplete` has no reader on any restore or restore-point-selection path, so the field documented as the last-resort identifier of an unusable artefact never rejects one — and `--latest` prefers it, being newest. `BackupMetadata.refuseIncompleteCapture` is read on both restore paths, before the checksums and everything destructive — which is also the refusal `--latest` needs, since selection there has only the archive's name. No `--force` escape, deliberately: unlike a group missing components, a capture that reported it had not finished reading the database leaves nothing for a bypass to be a judgement about

### Wrong answer, wrong place

- [X] T103 `getPodForServiceWith`'s name fallback is still the bare token-boundary match while the location decision uses the ownership rule, so resolution and location give two answers from the same evidence — and discovery execs into a foreign pod, adopting *its* connection URL as the endpoint restore writes into. The fallback already went through `deploymentClaimsResource` (49b5790); what still differed was the *policy*, hard-coded `unanchoredNameClaims` at each call site. It is now `unanchoredNamePolicyFor(service)` at all four — the pod resolver, the running check, the location decision and the workload resolver — so the choice follows the service and one listing yields one answer. `postgres-database-0` in an unlabelled namespace is refused by resolution and by location alike; the app services keep the permissive reading they ship with. **This label-guards `getPodForServiceWith`'s fallback, so T074's second half is covered here — narrow T074 rather than duplicating it**
- [X] T104 `findWorkloadResourceWith` derives release prefixes per-kind while `deploymentClaimsService` derives them namespace-wide, so a chart labelling StatefulSets but not Deployments still scales a foreign workload to zero. Both listings are now gathered before either is judged, and `namespaceReleasePrefixes` derives the prefixes from every kind together. Label evidence across all kinds is also read before any name match on any kind, which is the precedence `claimedPodNamesWith` already applies to pods. A test drives the exact topology and catches the old code resolving `redis-cache` as `cache`
- [X] T105 `locateServiceWith` is strictly narrower than the resolver's own fallback, so a CloudNativePG task-manager database — the topology the ownership doc block names as the case it fixes — is classified external and restore is refused outright. Fixed by widening the *evidence*, not the policy, so T103's narrowing stands: `nameIsServiceOwnName` claims a resource named for the service itself — nothing before it, and nothing after it but an ordinal or a hash — which is what `task-manager-db-1` is and what `postgres-database-0` (a release this deployment never declared) and `task-manager-db-exporter` (a different component, a word after the service) are not. It holds whether or not a prefix was declared, so the CNPG cluster is internal in a Helm-labelled namespace and in a bare one, and the resolver reaches the same pod
- [X] T106 `fetchPostgresCredentials` discards `applyPrefectConnection`'s bool and marks discovery read unconditionally — the exact defect the return value was added to fix at the other call site. The read is now recorded only when the URL supplied something, so a typo in the deployment's own connection variable no longer suppresses `ensurePostgresDiscovery`. Table-driven test over the three shapes: a URL that parsed, one that did not, and a container exporting none
- [X] T107 `redactDatabase` and `isNeo4jCluster` exec into `"database"` unconditionally, so `--redact` reproduces the FR-008 misdiagnosis after the gate established the database is external, and still passes credentials as argv. **Partial.** The gate half was already fixed in `e49b4be` — both now call `externalCaptureSourceFor(serviceNeo4j)` first, both are reached after `prepareDatabaseCapture`, and `TestRedactDatabaseRefusesAnExternalDatabase` / `TestIsNeo4jClusterReadsWhatTheProbeObserved` cover them; the box was simply never ticked. So the gate half was the whole of the defect this task names, and it is fixed and covered. The internal argv exposure is real, pre-dates the branch (all 10 sites present unchanged at base `8186fcf`), and is out of scope here — see T121
- [X] T108 The capture pod's deadline budgets one operation bound for a pod hosting two full-bound operations (capture, then a copy that opens its own `externalDBBound`), so the cluster kills it mid-copy after a capture that succeeded. `externalDBProbeDeadline` was fixed for exactly this and its sibling was not. `externalDBCaptureDeadline` now multiplies the bound by `externalDBCaptureFullBoundCalls`, named and documented as the two operations the pod hosts; the short control-bound calls around them stay covered by the margin.
