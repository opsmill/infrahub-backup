# Critique Report: Storage Figures for the Task Manager Database in Troubleshooting Bundles

**Date**: 2026-10-26
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: PROCEED WITH UPDATES

---

## Executive Summary

The spec follows the PRD closely and answers its three open questions with sources. The plan rests on behavior verified against PostgreSQL 18: the read-only session, the time limit that PostgreSQL enforces, the query that keeps running after its client is killed, and the join settings that avoid temporary files. One finding blocks task generation. The planned end-to-end time-limit test holds an `ACCESS EXCLUSIVE` lock that also blocks the always-on storage query, so that collector would stall for 60 seconds and fail in the same test. This was verified: `pg_total_relation_size` waits for the lock until `statement_timeout`. The same lock behavior, together with the credential lookup, also explains when support would get no storage figures at all. Both points are fixed in the spec and plan below.

## Engineering Lens Findings

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | Recommendation | The breakdown collector and the storage collector each need the credentials, the replica check and the error classification. The plan puts these in one shared runner, which is the right boundary, but does not say where the resolved credentials are cached. | Cache them on `collectContext` for the run, as the plan says, and add a unit test that the `task-manager` `env` lookup runs once for both collectors. Applied to research R14. |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E2 | Must-address | The end-to-end time-limit test (research R14, quickstart scenario 4) holds `LOCK TABLE artifact IN ACCESS EXCLUSIVE MODE` for the whole run. The always-on storage query runs earlier in the plan and calls `pg_total_relation_size('artifact')`, which waits for the same lock. Verified: with `statement_timeout=2000` the size function fails with `canceling statement due to statement timeout`, while `to_regclass` and `pg_stat_user_tables` do not wait. The test would therefore stall for 60 seconds, record `task-manager-db-storage` as failed, and its assertions would not cover that. | Make the test-only variable lower both limits (storage and breakdown) and rename it `INFRAHUB_TASK_MANAGER_DB_QUERY_TIMEOUT`. The test then also asserts that `task-manager-db-storage` failed with `timed out after <limit>`, which covers the second sentence of FR-009 from start to end. Update research R14, `contracts/cli.md` and quickstart scenario 4. Applied. |

### Security and Privacy

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E3 | Recommendation | The password reaches `psql` as `docker exec -e PGPASSWORD=...` or `kubectl exec ... -- env PGPASSWORD=...`. Other users of the operator's host can view it in the process list, and a Kubernetes API server that logs request URIs records it in its audit log. `infrahub-backup create` has the same exposure today, and the PRD asks for the same approach, so this is not new to the feature. The bundle itself stays clean (FR-017). | Record the limitation in research R10. Propose a follow-up issue, for both tools, that passes the password on standard input (`sh -c 'PGPASSWORD="$(cat)" exec psql ...'`). Research note applied; the issue is not opened by this workflow. |

### Performance and Scalability

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E4 | Recommendation | The `events` and `log` breakdowns scan the whole table. On tables of tens of gigabytes they can reach the 5-minute limit, which the PRD accepts (the table is recorded as failed). The operator has no hint of how long each table will take. | No change to the queries. The documentation says that a table that reaches the limit is recorded as failed and that the figures of the other tables are still collected. Applied to `contracts/cli.md`. |

### Testing Strategy

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E5 | Recommendation | On multi-container pods, such as CloudNativePG pods, `kubectl exec` writes `Defaulted container "postgres" out of: ...` to the error output before the command's own output. The error classifier must not pick that line as the cause. | Add error-output fixtures that start with that line to the classification tests. Applied to research R14. |

### Operational Readiness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E6 | Recommendation | `PGAPPNAME=infrahub-collect` makes the tool's sessions visible in `pg_stat_activity`, but an operator who must stop a breakdown at once does not know this. | Document in the breakdown section how to stop the tool's query immediately: `SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE application_name = 'infrahub-collect'`. Applied to `contracts/cli.md`. |

### Dependencies and Integration

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E7 | Question | FR-014 depends on the `task-manager-db` pod selectors matching CloudNativePG pods. | Resolved: the HA example in opsmill/infrahub (`development/k8s/taskmanagerdb.yaml`) labels the pods `infrahub/service: task-manager-db` through `inheritedMetadata`, which the existing `infrahub/service=<service>` selector matches. A CloudNativePG cluster without that label is reported as not deployed, as backup already treats it. |

## Cross-Lens Insights

| ID | Finding | Product Impact | Engineering Impact | Suggestion |
|----|---------|---------------|-------------------|------------|
| X1 | The credential lookup reads the connection URL from the `task-manager` container. When the database has filled its disk, the Prefect server is often down or restarting, and on Kubernetes the lookup then falls back to the defaults `postgres` and `prefect`, which the Helm chart's PostgreSQL rejects. | Support gets no storage figures in the case they matter most. | The fallback produces a login failure, which looks like a configuration problem rather than the real cause. | Before the defaults, read the owner, password and database from the `task-manager-db` container's own environment (`POSTGRES_USER`, `POSTGRES_PASSWORD`, and `POSTGRES_DB` or `POSTGRES_DATABASE`, the names used by the official image and the bitnami image; to verify on the end-to-end kind cluster). Never stage that output. Applied to research R8 and the spec's Assumptions. |
| X2 | The lock behavior in P4 and E2 has one root: every size function takes a lock on its table. | Figures can be missing during an upgrade. | Tests that hold locks must account for the always-on query. | Covered by the P4 and E2 changes. |
