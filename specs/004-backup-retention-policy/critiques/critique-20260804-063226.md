# Critique Report: Backup Retention Policy

**Feature**: `specs/004-backup-retention-policy` | **Date**: 2026-08-04 06:32 UTC
**Artifacts reviewed**: spec.md, plan.md, research.md, data-model.md, contracts/cli.md, quickstart.md, `.specify/memory/constitution.md` (v1.1.0)
**Mode**: autonomous (speckit-opsmill-prep) — Must-Address fixes applied in the same pass, recorded under Remediation.

## Executive Summary

The spec and plan are in strong shape: the problem is evidenced (issue #151, helm#80 dependency), scope is aggressively carved, the selection core is designed as a pure, floor-enforcing function, and every constitution principle is explicitly satisfied with no violations. Two Must-Address gaps were found, both cheap to fix and both about **undefined behavior at boundaries** rather than flaws in the chosen design: (1) what v1 does when the Plakar backend is selected while retention is requested, and (2) what happens *within* a prune leg when an individual deletion fails. Five recommendations harden testing, timeouts, and documentation. Verdict: **⚠️ PROCEED WITH UPDATES** — fixes applied, then proceed to `/speckit-tasks`.

## Product Lens Findings

### 3a. Problem Validation — sound

Grounded in a filed operator-pain issue (#151) with a concrete downstream dependency (helm#80 nightly sync). Scope carving (GFS tiers, per-project policies, merged timelines all out) keeps v1 sharp. No findings.

### 3b. User Value Assessment — one gap (X1)

US1–US3 each deliver standalone value and are independently testable. The MVP question (local-only first) was explicitly decided during grilling in favor of including S3 in v1 — not relitigated here. **Gap (X1)**: the spec defines P3 for the Plakar backend but never says what v1 does when a user selects `--backend plakar` *and* asks for retention. Silent no-op on `create` would let an operator believe retention is active when it is not — the exact unattended-rot failure this feature exists to prevent; `prune` on plakar doing nothing (or quietly pruning a local dir that isn't the backup store) is worse. See X1 in the findings table.

### 3c. Alternative Approaches — adequately recorded

research.md R4/R5 document rejected alternatives (aws-sdk, lifecycle-rules-only, refuse-always UX) with reasons. No findings.

### 3d. Edge Cases & UX — one documentation gap (P1)

Edge-case coverage is unusually thorough (stalled schedule, decoys, empty locations, partial permissions, encrypted archives, from-files). One interaction found: `restore` from an S3 URI downloads the archive into `BackupDir` under its original (old) name — that copy becomes a legitimate retention candidate on the next scheduled run. Correct behavior, but surprising if undocumented (P1, docs note).

### 3e. Success Measurement — sound

SC-001–SC-006 are measurable and technology-agnostic; SC-003/SC-005 are invariants enforceable in tests. Rollback for a CLI flag feature is "stop passing the flags" — no further machinery warranted. No findings.

## Engineering Lens Findings

### 4a. Architecture Soundness — sound, one drift guard missing (E2)

Pure selection function with the floor inside it (R2) makes the non-negotiable invariant structural. The `storageLocation` seam is an in-package interface, not a new layer — consistent with Constitution I. **Gap (E2)**: `generateBackupFilename` (writer) and `parseBackupName` (reader) form an implicit format contract with no test tying them together; a future format change would silently make new backups invisible to retention — unbounded growth returns without any error. A round-trip unit test closes this permanently.

### 4b. Failure Mode Analysis — one undefined behavior (E1), one hardening (E3)

Leg-level aggregation is well-specified (FR-008), but **within-leg** behavior is not: if deletion 3 of 10 fails (EACCES, transient S3 500), does the leg stop or continue? Stopping strands reclaimable space behind one bad object and makes outcomes order-dependent; the spec must pick one. Recommendation applied: best-effort — attempt every candidate, collect per-deletion errors, report all (E1, Must-Address). Separately, the existing `S3Client.Upload` bounds itself with a 30-minute context timeout while the new List/Delete calls have no stated bound — an S3 endpoint that hangs would hang a scheduled backup run forever (E3).

### 4c. Security & Privacy Review — defense-in-depth notes (E5, P1)

No new trust boundaries: credentials come from existing config, deletion targets are derived only from `ReadDir` base names / prefix-scoped keys filtered through an anchored regex. Two hardenings: add an explicit test that names containing path separators can never match `parseBackupName` (structurally impossible with `^...$` on a base name, but the test documents the guarantee — E5); docs should show a least-privilege S3 policy scoped to the prefix now that delete/list are required (P1).

### 4d. Performance & Scalability — sound

O(10³–10⁴) candidates, paginated listing, in-memory sort — no bottleneck at 10x. Per-object `RemoveObject` chosen deliberately for per-deletion logging; batch API recorded as a future optimization (R4). No findings.

### 4e. Testing Strategy — strong core, one testability seam (E4)

Selection/parsing/validation are pure and table-tested; e2e covers wiring. **Gap (E4)**: the interactive confirmation path is untestable unless the prompt is injectable — the repo already solves this in `updater.Proceed(assumeYes, …)`; mirror that seam so decline/accept/non-TTY paths get unit coverage instead of remaining a manual-only path.

### 4f. Operational Readiness — sound

Per-deletion real-time logging (Principle V), unmistakable "backup succeeded; retention failed" error contract, docs updates planned, release-notes callout listed in plan. CLI feature → no alerting/migration machinery needed. No findings.

### 4g. Dependencies & Integration Risks — sound

Zero new dependencies (minio-go v7 and kloset already direct). helm#80 consumes only the flag surface defined in contracts/cli.md. Backward compatibility: behavior is bit-identical when no retention flag is set. No findings.

## Cross-Lens Insights

- **X1 (Product × Engineering)**: the undefined Plakar-backend-in-v1 behavior is simultaneously a user-trust gap (silent no-op teaches operators retention is on when it isn't) and an implementation ambiguity (a task author would have to guess). One decision fixes both — and the asymmetric resolution (warn-and-skip on `create`, hard error on `prune`) follows from each command's contract: `create`'s job is the backup; `prune`'s *only* job is retention.
- The floor-inside-selection design (R2) is the strongest single decision in the plan: it converts the constitution's safety demand into a property provable by a unit test rather than a discipline imposed on call sites.
