---
title: Infrahub Collect
---

Use Infrahub Collect to gather everything OpsMill support needs to investigate an issue — service logs, diagnostic status, configuration, Infrahub product telemetry (the daily usage snapshots that Infrahub stores in its own database, described in [Review before sharing](#review-before-sharing)), and metrics — into a single local archive. Run it when support asks for logs, or to attach diagnostic data to a support request. The same command produces the same bundle on Docker Compose and Kubernetes.

## What a collection changes in your deployment

A default collection, without `--benchmark` or `--include-backup`, reads logs and status from your deployment. Unlike `infrahub-backup create`, it never stops, restarts, or scales any container or pod, so you can run it against a production instance at any time, including while the instance is degraded. If a service is down, collection continues with the rest and records the failure in the manifest. A partial bundle is still a useful bundle — a degraded instance is precisely when you need one.

A default collection writes two temporary files inside a container. When the collector that wrote a file finishes, including when that collector fails, `infrahub-collect` runs `rm -f` in the container to delete the file:

- `/tmp/infrahubops_collect_prefect_events.py` in a `task-worker` container, or in the `task-manager` container when no task worker runs. This is a script that reads recent Prefect events, because the Prefect CLI has no command that prints events and exits.
- `/tmp/infrahubops_telemetry_export_<random>.json` in a `task-worker` container. `<random>` is a random string of lowercase letters and digits that differs on each run, so two collections against the same deployment at the same time do not overwrite or delete each other's file. `infrahubctl telemetry export` writes this file, and `infrahub-collect` copies it into the bundle.

If `rm -f` fails, `infrahub-collect` prints a warning that names the file and the service, the collection continues, and the file remains in the container. Delete the file by hand.

Two opt-in flags change more than that:

- `--benchmark` creates a container (Docker Compose) or a pod (Kubernetes) from the OpsMill benchmark image, and runs `docker rm -f` or `kubectl delete pod` to delete it after the benchmark. If that command fails, `infrahub-collect` prints no message, and the container or pod remains. Its name contains the collection ID, for example `infrahub-collect-benchmark-20260702-141530` for collection ID `20260702_141530`. Delete it with `docker rm -f <name>` or `kubectl delete pod <name> -n <namespace>`.
- `--include-backup` runs the standard backup, which can stop the Infrahub services while the snapshot is taken.

On Kubernetes, each of these modes needs different permissions. See [Kubernetes permissions for Infrahub Collect](./kubernetes-permissions.mdx).

The binary is self-contained. By default, collection works offline: it uses your existing Docker or kubectl access and performs no network access beyond the deployment itself. The one exception is the opt-in `--benchmark`, which downloads a benchmark image.

## Collect or back up?

A troubleshooting bundle contains diagnostics for support to read; a [backup](../backup/create.mdx) is a restorable snapshot of your data. They are separate operations with different safety profiles — a default collection never stops containers, while a backup can stop containers while the snapshot is taken. When support asks for both, run `infrahub-collect create --include-backup` to produce them in one run.

## What a bundle contains

Each bundle is a single `tar.gz` archive. Inside, every file lives under a top-level `bundle/` directory, alongside a `bundle_information.json` manifest that records an explicit outcome — success, failed, or skipped — for every collector, so support can see what was captured and what was not.

| Collector | What it gathers |
|---|---|
| Service logs | Container logs for every service and replica, plus previous-container logs for restarted pods |
| Database | Neo4j server logs (full log directory with `--include-queries`) |
| Message queue | RabbitMQ queues, exchanges, bindings, connections, and status |
| Cache | Redis info, client list, configuration, and slow log |
| Task worker | Prefect worker state, one directory per replica |
| Task manager | Work pools, work queues, recent flow runs, the pending and running flow and task runs, events, and automations |
| Server | Version, installed packages, API information, configuration, schema, and masked environment variables |
| Telemetry | The Infrahub product-telemetry snapshots stored in your Infrahub database, by default from the current day and the 30 days before it (`--telemetry-days`); absent when the deployment has no snapshots in that window |
| Metrics | Container resource usage |
| Backup (opt-in) | A standalone backup produced by the standard backup behavior and referenced in the manifest, not embedded in the archive (`--include-backup`) |
| Benchmark (opt-in) | Host resource benchmark results (`--benchmark`) |

The layout is identical on Docker Compose and Kubernetes.

## Review before sharing

Masking is based on key names: environment variables and configuration keys containing `password`, `secret`, `token`, or `key` are replaced with `********` before they are written to the bundle. Secrets stored under other key names are not detected. Service logs are collected as-is, and database query logs (`--include-queries`) can contain customer data. Review the bundle contents before sharing it.

The telemetry export, `telemetry/telemetry-export.json`, is written exactly as `infrahubctl telemetry export` returns it, without masking. It holds the daily snapshots that Infrahub stores in its own database. Infrahub stores these snapshots even when reporting to OpsMill is turned off with `INFRAHUB_TELEMETRY_OPTOUT`, so bundles from opted-out deployments also contain them. Each snapshot records:

- The snapshot's identifier, type, payload format, and the time Infrahub created it
- The Infrahub version and the deployment identifier
- A SHA-256 checksum that Infrahub stores to verify the snapshot's integrity
- Whether Infrahub sent the snapshot to OpsMill
- The telemetry payload, which the Infrahub documentation describes as anonymous usage data with no personally identifiable information:
  - The Infrahub version, the deployment type, and the platform: Python version, operating system, and CPU architecture
  - Counters about the graph, schema, and features in use
  - Counts of active accounts, account groups, and open branches
  - Database, worker, and infrastructure statistics
  - Activity over the previous day, such as logins, validation checks, artifact generation, branch operations, and webhook deliveries

See [What telemetry does Infrahub send?](https://docs.infrahub.app/faq#what-telemetry-does-infrahub-send) and [Local telemetry storage](https://docs.infrahub.app/deploy-manage/run-observe/telemetry) in the Infrahub documentation. That description covers the telemetry export only: Infrahub Collect does not anonymize the logs, schema, or configuration in the rest of the bundle.
